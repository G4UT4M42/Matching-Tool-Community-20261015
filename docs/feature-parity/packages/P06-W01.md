# P06-W01 — Exact offline statement parsing and event identities

Status: IN_PROGRESS. Backend acceptance passed; final parity/format coverage and integrated release gates remain open.

## Existing behavior and defect evidence

Reference the F02 source audit in `../release-program/FEATURE_PARITY_AUDIT_20261013.md` (relative to the feature-parity parent directory). Prior bank/card ingestion coerced values heuristically, hardcoded EUR and used near-date/amount heuristics to suppress events. The initial seven-test statement regression reproduced six incorrect outcomes.

## Current implementation

- `src/import/statement-parser.ts`: strict CSV/XLSX decoding, amount/date/currency validation, account identity, stable references and malicious-workbook rejection.
- `src/import/file-import.ts`: full validation before writes, source/account/reference identity maps, replay protection, conflict handling, exact event preservation and SQLite transaction rollback.
- `src/storage/statement-transaction.ts`: versioned checksummed journal, SQLite commit marker, atomic JSON participant and restart recovery.
- `src/server/routes/statement-import.ts`: reviewed authenticated multipart boundary with file/field limits and sanitized errors.

No fuzzy date/amount match may delete a distinct source event. Reference-less overlap between different files is an explicit reconciliation conflict, never silently skipped or counted twice. A repeated identical statement is idempotent. Two identical rows within one statement remain two events.

## Security and financial invariants

Amounts must fit the exact integer range and the selected currency precision. Invalid dates and decimals reject the whole file. Debit and credit columns cannot contradict each other. No currency conversion is fabricated. Users select a local account identifier; conflicting statement metadata is rejected. File names never become server filesystem paths. No imported operation executes a payment.

CSV and XLSX inputs are bounded to 10 MiB and 20,000 rows. Workbook members, compression output, CRCs, formulas and external relationships are checked before processing. Authentication/origin checks precede multipart parsing. All input rows are validated before persistence.

Backend source and tests are typechecked. The complete backend acceptance set currently passes 101 tests. This is not full P06-W02 browser or P12 upgrade acceptance.

## Recovery and rollback

Keep the journal until both participants agree. On startup, the SQLite audit commit marker determines whether to restore the before or after JSON snapshot. Unknown checksums, missing/corrupt files and invalid markers keep operations closed rather than overwrite newer state. Never delete a recovery journal to make a failed test pass.
